## Response envelope

Most JSON operations use `status: success` with `data`, or this error shape:

```json
{
  "status": "error",
  "message": "Missing required scope.",
  "code": "MISSING_SCOPE"
}
```

Some operations return a message, no content or a route-specific response; use the endpoint reference. Health uses `{ "status": "ok" }`. Paginated lists add supported cursor fields. Error `details`, when present, contains the bounded information documented for that error, such as field-validation or allowance information.

Use the HTTP status and `code` for control flow; messages can change. Never display or depend on raw debugging data.

## Common errors

| Status        | Code or situation                                    | Action                                                                                                           |
| ------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `400`         | `BAD_REQUEST`, `INVALID_JSON`                        | Correct the request shape, values or currency precision.                                                         |
| `401`         | `AUTH_FAILED`                                        | Check credential state, timestamp and the exact signed bytes.                                                    |
| `403`         | `MISSING_SCOPE`, `SERVICE_NOT_INCLUDED`, `FORBIDDEN` | Check permission, enabled product and selected business.                                                         |
| `404`         | `NOT_FOUND`                                          | Confirm the resource ID and business context.                                                                    |
| `409`         | `IDEMPOTENCY_CONFLICT`                               | Resolve a key/body mismatch or conflicting transfer quote/reference identities; do not invent a replacement key. |
| `409`         | `INSUFFICIENT_BALANCE`                               | Confirm the total source debit, including fees, and available funds.                                             |
| `409`         | `INSTANT_CONVERSION_LIMIT_EXCEEDED`                  | Read the returned safe allowance details and reconcile any earlier attempt.                                      |
| `413` / `414` | Request body or URL too large                        | Reduce the request to the endpoint's limits.                                                                     |
| `422`         | Payout transaction or monthly limit exceeded         | Review current business limits. Repeating unchanged input does not bypass the cap.                               |
| `423`         | `COMPLIANCE_REVIEW_REQUIRED`                         | The operation needs review; do not create replacement payments to bypass it.                                     |
| `429`         | `RATE_LIMITED`                                       | Honour `Retry-After` when supplied and reduce request rate.                                                      |
| `500` / `503` | Temporary or unexpected service failure              | Back off reads; reconcile uncertain writes under their replay contract.                                          |
| `501`         | `NOT_IMPLEMENTED`                                    | The requested operation is not available.                                                                        |

Codes are additive. Handle unknown codes as errors using their HTTP status. Individual endpoints document additional codes and limits.

## Retries

Read requests can use exponential backoff with jitter and a bounded attempt budget after temporary failures. A timeout or `5xx` on a write can occur after acceptance. It is not evidence that nothing happened.

Follow [operation-specific retry rules](/guides/idempotency): retain the original wallet/account key and body, the network setup request ID, or the transfer quote/reference. Do not generate a new key or quote merely to escape an error. After changing a rejected request, first establish that the original attempt has no unresolved outcome.

## Request IDs and safe diagnostics

Retain the `x-request-id` returned by Ledig. A client-supplied request ID must use 8–128 characters from letters, digits, `.`, `_`, `:`, or `-`. A valid value is preserved.

Record the request ID, time, environment label, HTTP method, path template, status and error code. For example, record `/v1/transfers/{id}` rather than a complete URL with sensitive query values.

Never log credentials, signatures, complete signing payloads, complete request/response bodies, customer documents or upload capability URLs. Redact customer details before sharing diagnostics with support.

## Debugging checklist

1. Confirm `LEDIG_API_BASE_URL` matches the [approved environment](/introduction#environments).
2. Check the timestamp uses Unix seconds and the local clock is synchronized.
3. Check that signing used the exact path, query and body sent; compare locally without logging their sensitive contents.
4. Confirm the required scope and service are enabled for the selected business.
5. For delegated requests, confirm HMAC v2 and the business-selection headers.
6. Contact [admin@ledig.io](mailto:admin@ledig.io) with the request ID and redacted diagnostics if the outcome remains uncertain.
