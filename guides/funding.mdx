## Fiat funding accounts

`GET /v1/virtual-accounts/{currency}` reads the profile's existing active account for that currency. It never creates one. If the profile has no account, the route returns `404`.

```http
GET /v1/virtual-accounts/NGN
```

```json
{
  "status": "success",
  "data": {
    "id": "vis_example",
    "currencyCode": "NGN",
    "accountName": "Example Business",
    "accountNumber": "0123456789",
    "bankName": "Example Bank",
    "bankCode": "000000",
    "status": "active"
  }
}
```

### Request an account

If the profile has no account for the currency, request one with `POST /v1/virtual-accounts`. The `Idempotency-Key` header is **required**:

```http
POST /v1/virtual-accounts
Idempotency-Key: 8f14e45f-ea3b-4c1a-9d5e-2f7c1a6b9d10
Content-Type: application/json
```

```json
{
  "currency": "NGN",
  "accountName": "Example Business"
}
```

`provider` is optional. A completed request returns `200` with the issued account. A durable request that is still pending returns `202`:

```json
{
  "status": "success",
  "data": {
    "id": "var_example",
    "currency": "NGN",
    "status": "pending_provider",
    "missing": [],
    "accountId": null
  }
}
```

`status` is `requested`, `manual_review`, `pending_provider` or `completed`. `missing` lists anything the request still needs; `accountId` is populated once an account exists.

<Warning>
  `GET` no longer creates an account. If your integration relied on the old get-or-create behaviour, migrate to `POST /v1/virtual-accounts` with an `Idempotency-Key`.
</Warning>

- Reuse the same `Idempotency-Key` when retrying the same request. Changed inputs with the same key return `409`.
- Responses are `Cache-Control: no-store` because funding instructions can change. Fetch them when you need them; do not cache them in your UI or logs.
- Use the returned account number for bank transfers. Do not expose another business's account details.

## Crypto deposit wallets

Create a wallet with `POST /v1/wallets`. The `Idempotency-Key` header is **required**:

```http
POST /v1/wallets
Idempotency-Key: 8f14e45f-ea3b-4c1a-9d5e-2f7c1a6b9d10
Content-Type: application/json
```

```json
{
  "nickname": "Treasury",
  "coin": "USDT",
  "network": "TRC20",
  "memo": "optional"
}
```

```json
{
  "status": "success",
  "data": {
    "id": "wal_example",
    "address": "TExampleAddress",
    "memo": "",
    "nickname": "Treasury",
    "coin": "USDT",
    "network": "TRC20",
    "createdAt": "2026-10-22T09:00:00.000Z"
  }
}
```

- Reuse the same `Idempotency-Key` when retrying the same request. A different body with the same key returns `409 IDEMPOTENCY_CONFLICT`.
- If the response includes a memo or tag, send it with every deposit to that address. A deposit without the required memo may not be credited.
- `GET /v1/wallets` lists the profile's wallets. `GET /v1/wallets/{id}` returns one.
- Wallet creation can wait on provider issuance. A conflict that says issuance is awaiting reconciliation means the wallet may already exist; retry later instead of creating another one.
- A wallet has an address, not a separate balance. Balances stay at profile and currency level. See [Balances](/guides/balances).
