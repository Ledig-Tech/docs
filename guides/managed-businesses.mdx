---
title: "Managed businesses"
description: "Complete a managed business's onboarding while keeping its funds and approvals separate."
---

An institution can create and manage standard businesses. Each managed business keeps its own onboarding, product access, limits, recipients, balances and transactions. A management relationship does not approve the business or combine its funds with the institution's funds.

## Choose the correct context

Parent-managed onboarding requires the institution's `merchants` service and `merchants:read` or `merchants:write` scope. Authenticate with its API key or an accepted dashboard session.

Keep the institution selected in `X-Ledig-Business-Id` and, if supplied, `X-Ledig-Acting-Business-Id`. Put the child's ID in `/v1/managed-businesses/{businessId}/onboarding`. A pending child may be onboarded through these paths even when its directory entry has `canAct: false`.

This is an own-parent request, so HMAC v1 remains valid; HMAC v2 is also accepted. Later financial requests select the child and require v2 for an API key. See [Authentication](/auth/authentication#managed-business-delegation).

## Create the application

1. Call `GET /v1/managed-businesses` to read the institution's current relationships. This directory is not paginated.
2. Call `POST /v1/managed-businesses/applications` with an `Idempotency-Key` and only `businessName` in the body:

```json
{ "businessName": "Example Trading Ltd" }
```

The accepted response includes `requestId`, `applicationId` and the child's `businessId`. Retain these values. Reusing the same key and name returns the original request; changing the name under that key returns `409`. This operation does not send an invitation or create an applicant login.

Use the returned child ID in the onboarding paths below. Do not supply another application ID in a body to select the application.

## Read and update sections

The following paths are relative to `/v1/managed-businesses/{businessId}/onboarding`:

| Method and path                       | Purpose                                                                    |
| ------------------------------------- | -------------------------------------------------------------------------- |
| `GET /`                               | Application status, correction instructions and verification progress.     |
| `GET /sections`                       | Section statuses, saved answers and the current `updatedAt` edit revision. |
| `GET /{section}`                      | Read one section.                                                          |
| `GET /{section}/options`              | Discover valid form values and document requirements.                      |
| `PUT /{section}`                      | Save answers using the endpoint's `{ "data": ... }` shape.                 |
| `POST /{section}/complete`            | Validate and complete a section.                                           |
| `POST /owners`                        | Add an owner or related party.                                             |
| `DELETE /owners/{ownerId}`            | Remove a related party.                                                    |
| `POST /owners/{ownerId}/verification` | Start or resume a required individual verification.                        |
| `POST /submit`                        | Submit the application for review.                                         |

Only the relevant individual should complete their identity and liveness verification. A verification session is a short-lived capability; keep it out of logs and share it only with that individual through the intended flow.

## Preserve the edit revision

Parent-managed applications may be edited by the institution and an applicant using a sharing link. Use the revision to avoid overwriting another person's changes:

1. Read `data.updatedAt` from `GET .../onboarding/sections` without changing its formatting.
2. Send that exact value, surrounded by double quotes, in `If-Match` when saving or completing a section, adding or removing an owner, registering or completing a document upload, or submitting.
3. A successful mutation returns the next quoted revision in `ETag`. Use that value for the next mutation.
4. Missing or stale revisions return `409`. Preserve unsaved input, reload the current state and reconcile it before trying again. Do not automatically overwrite the new revision.

For example, build the header in your client with `JSON.stringify(sectionList.data.updatedAt)`. After a successful write, copy `response.headers.get("ETag")` directly into the next `If-Match` header.

A sequence of writes is not one atomic edit. Earlier steps may have succeeded before a later step conflicts, so reread the saved application before resuming.

## Upload and complete each document

An upload has three steps. A successful file transfer alone does not mean the document is accepted.

1. **Register:** call `POST .../onboarding/documents` with the current `If-Match` and the required document fields. Compute the SHA-256 checksum from the exact file bytes and supply the exact `sizeBytes`. Use the requirement and document kind returned by the options endpoint. Retain `data.document.id`, `data.upload` and the response `ETag`.
2. **Transfer:** PUT the exact file bytes to `data.upload.uploadUrl` before it expires, using all returned `requiredHeaders`. Do not add Ledig API authentication to the upload URL. In browsers, let the browser set `Content-Length` from the file bytes.
3. **Complete:** after the PUT succeeds, call `POST .../onboarding/documents/{documentId}/complete` with the revision from registration in `If-Match`. Adopt the returned `ETag` and the durable `data.document` receipt before the next edit.

PDF, JPEG and PNG files are supported, up to 50 MiB each. Read `maxSizeBytes` and `allowedMimeTypes` from the returned upload policy. Completion checks the stored size, MIME type, checksum and readability. An invalid file receives a file-specific correction; replace it rather than repeatedly uploading the same damaged bytes. A temporary validation outage requires retrying completion of the same registered file after recovery, not creating another upload.

A known failed or interrupted PUT must not be shown as complete. If an outcome is uncertain, retain the document ID and reconcile its state before replacing it. Repeating completion with a current revision preserves the original receipt; stale revisions still conflict.

A validation failure can include a quoted `x-onboarding-committed-revision` for that exact failed completion or submission. Apply it only to the matching response, preserve unrelated unsaved edits, and use the returned correction. An ordinary error or a later read is not permission to overwrite another editor's work.

<Warning>
  Upload URLs and required upload headers are temporary credentials. Do not log
  them, persist them in analytics or send them to another service. Document
  receipt means the file passed upload validation; it does not mean the business
  has been approved.
</Warning>

## Submit and follow corrections

Call `POST .../onboarding/submit` with the current revision after completing the required sections, documents and individual checks. Submission begins review; it does not approve or activate the business.

Read the application to follow status and verification progress. When `status` is `changes_requested`, `reviewReason` contains the customer correction instructions. Apply corrections through the same sections and upload flow. Do not infer approval from a file upload or a single verification result.

## Sharing links

A sharing link lets an applicant read, edit and submit this application without a Ledig account. It does not grant financial access, dashboard membership or approval authority.

| Operation                   | Path after `/onboarding`                                              |
| --------------------------- | --------------------------------------------------------------------- |
| Read current session status | `GET /share`                                                          |
| Create a link               | `POST /share` with `{}`                                               |
| Replace a link              | `POST /share` with `replaceSessionId` from the latest status response |
| Revoke a link               | `DELETE /share/{sessionId}`                                           |

Keep the institution selected for these operations. Links expire after seven days and can be revoked earlier. Replacement revokes the previous link and its browser sessions; a stale replacement ID returns `409`.

The URL is returned once and is not emailed automatically. If the creation response is lost, read the current session status and explicitly replace that session. The original plaintext URL cannot be recovered.

<Warning>
  Anyone with a sharing URL can access this application's personal and business
  information and edit or submit it. Deliver it only to the intended applicant.
  Keep it out of logs, analytics and shared records.
</Warning>

## Use the managed business after onboarding

An active business with the required product access can be selected for supported financial operations. Set `X-Ledig-Business-Id` to the child and sign the request with HMAC v2 using the institution's key. Current relationship and permission checks still apply. Each operation uses the child's funds, limits and approved destinations.

Onboarding is separate from moving money: `canAct`, business status, product access and the financial operation's own checks determine what is available.
